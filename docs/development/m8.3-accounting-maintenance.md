# M8.3 setup-managed accounting maintenance

Dates: 2026-10-17–18. Status: local checks and the build-scoped installed cases
below passed. LocalPIN remains experimental; independent review, physical
hardware and signed-candidate gates remain open.

## Change and safety boundary

[ADR 0020](../adr/0020-setup-accounting-maintenance.md) makes the fresh-owner
`localpin setup` command arrange offline password-accounting maintenance after
explicit approval to save work and sign out. A fixed packaged system service
preserves every account's native failures, atomically selects persistent
accounting, restores password login, and publishes only a nonsecret UI hint.
The packaged KDE launcher opens the installed normal-user wizard once per
request. Fresh password enrollment, actual unlock tests, console recovery and
explicit activation are retained.

The service excludes old authentication workers before copying; it cannot copy
live counters or allow old parsed PAM configuration to resume afterward. Its
root-owned backups/journal retain interruption evidence. Conflicting or changed
accounting is never overwritten or reset. Unknown states require explicit
recovery; volatile state lost before a durable snapshot cannot be reconstructed.

## Installed observations

The [M8.3 harness](../../experiments/m83/README.md) uses an independently cloned
Fedora KDE 44 x86_64 VM with SELinux enforcing, a private managed TPM emulator,
and synthetic accounts. The original VM remains off; the guards reject backing
disks, host filesystem shares and physical devices. Raw terminal buffers,
passwords, PINs and native counter snapshots remain guest-private.

The final boundary-test [environment record](../../experiments/m83/results/guest-environment.json)
identifies Linux `7.2.10-200.fc44`, systemd `259.9-1`, PAM `1.7.2-2`, RPM
`6.0.2-1` and Plasma `6.7.5-1`. It retains the stock local authselect profile
with faillock and fingerprint enabled; this does not establish physical
fingerprint support.

### Migration, resumption and activation

The installed flow on RPM `0.1.0-0.1.alpha1.vm83.5.fc44` passed
[maintenance](../../experiments/m83/results/maintenance-complete.json): all
native counters from two synthetic accounts were preserved before any new
login, including a separate account's nonempty native failure history. Source
files and exact private backups retained their security metadata; only the
approved destination-only primary-group-to-root conversion occurred. The
journal recorded PID1 frozen and the eight present excluded cgroups frozen and
empty after old tasks were killed. All groups were thawed, the persistent policy
was installed, supported services returned, and no PIN was yet enrolled.

An actual full-password display-manager login then caused the **shipped KDE
autostart** to open the installed `localpin setup` in a real Konsole
[without manually restarting it](../../experiments/m83/results/automatic-resume.json).
That window performed fresh account-password verification, TPM-required PIN
enrollment and a ten-minute trial. Actual lock-screen
[PIN + Enter](../../experiments/m83/results/first-trial-pin.json),
[password](../../experiments/m83/results/first-trial-password.json), and a
[missing-module denial with password fallback](../../experiments/m83/results/first-trial-fallback.json)
passed without secret echo.

[Administrator recovery](../../experiments/m83/results/actual-console-recovery.json)
ran from a real text login on VT4 through ordinary wheel sudo, retaining the
physical-console ancestry required by the product. Dry-run made no change; real
recovery restored the six original PAM policy files, revoked account authority,
closed the gate and stopped the broker while retaining native counters. Actual
[password unlocking under the restored stock policy](../../experiments/m83/results/stock-password-after-console-recovery.json)
passed before repairing the missing-module fixture. Setup then required fresh
preparation, enrollment, a new trial and real PIN/password/fallback tests before
the [explicit final activation](../../experiments/m83/results/final-activation.json)
succeeded.

An [actual reboot](../../experiments/m83/results/active-reboot-before-login.json)

Full-password display-manager login preserved the active TPM enrollment; the
claimed UI marker remained unchanged and no setup process reopened. Actual
post-boot PIN + Enter and full-password lock-screen unlocking passed. The PIN
test left native password accounting unchanged.

[Active package removal](../../experiments/m83/results/erase.json) restored the
original KDE policy, revoked account authority and retained persistent native
accounting. An actual
[stock-password lock-screen unlock](../../experiments/m83/results/erased-password.json)
passed afterward. The successful normal-flow clone was then removed with the
exact-identity, independent-volume and no-reference guards; the original VM

### Final-candidate maintenance and recovery

The final `.11`
[actual worker-crash and same-boot recovery](../../experiments/m83/results/final-worker-crash-recovery.json)
passed with the exact packaged worker. The fixture established quiescent state
and actually frozen PID1 before SIGKILL. The real watchdog thawed the groups;
the actual authenticated emergency root console on VT2 invoked the installed
recovery helper. Recovery retained the original volatile policy and native
failure bytes/security metadata, recorded an aborted transaction, restored
login/network services and created no enrollment authority or resume hint.
The subsequent
[actual owner password login](../../experiments/m83/results/final-password-login-after-recovery.json)
recreated an active user manager, session bus and delegated `init.scope` with no
service repair. KDE was unlocked and the original non-owner failure record was
still unchanged before retrying normal maintenance.

That same preserved native history then passed the final `.11`
[normal migration](../../experiments/m83/results/final-maintenance-complete.json):
the exact original configuration and counter metadata were backed up, both
native tallies were copied with only the approved destination GID conversion,
the protected transaction became complete and all groups/services returned.
An actual full-password display-manager login then triggered the
[shipped automatic setup resumption](../../experiments/m83/results/final-automatic-resume.json)
in a real Konsole. The owner manager, bus and delegated subgroup were healthy
without repair; the wizard continued through elevated readiness to the real
preparation approval. Ordinary sudo cache was accepted in that resumed window;
the record does not claim a new sudo password prompt or PIN enrollment there.

The resumed wizard was paused before preparation, and final `.11`
[package removal](../../experiments/m83/results/final-erase.json) retained
persistent policy and every native tally. Actual
[stock-password unlocking](../../experiments/m83/results/final-erased-password.json)
passed afterward. The active-enrollment update/reboot/removal observations
remain the separately scoped `.5`/`.6` cases above.

### Pending-request reboot and package refusal

A separate fresh `.11` clone created a real request through the normal wizard,
with the delayed handoff held before worker execution by a temporary fixture.
The delayed service was stopped and its fixture removed while the protected
journal remained `requested`, with `isolation_requested=false`. Original
volatile policy and genuine native history remained unchanged; no product
journal was edited.

An [ordinary RPM erase](../../experiments/m83/results/pending-request-erase-refusal.json)
then refused in `%preun`. The installed helper and units remained intact with
clean RPM verification, and native policy/history and normal services remained
unchanged. No forced or script-skipping removal was used.

An [actual reboot](../../experiments/m83/results/pending-request-reboot-guard.json)
then reached the shipped emergency guard before display-manager or SSH startup.
After a real root emergency password login, the installed recovery helper
returned nonzero because the boot had changed and volatile authority was lost.
It retained the requested journal, original configuration and current tally
inventories, and created no empty counters, account authority or resume hint.
The original volatile failure record was absent after reboot; this is successful
refusal of unverifiable state, **not** counter preservation across that reboot.

### Refusals and corrections

The final concurrency test on `.9`
[refused a held native RPM lock](../../experiments/m83/results/native-rpm-lock-refusal.json)
before creating a maintenance request. The original graphical session and its
leader, normal services, volatile policy and non-owner failure record remained
unchanged. The native lock inode and metadata were retained and it could be
reacquired after the fixture released it; no actual package transaction was run.

The first actual `.9`
[worker-crash observation](../../experiments/m83/results/worker-crash-emergency-unavailable.json)
is **failed recovery acceptance**. The fixture bound the real worker to the
quiescent journal and frozen PID1, then proved SIGKILL. The watchdog thawed PID1
and reached emergency mode. However, the stock emergency shell exited
immediately, repeatedly retried normal startup, and hit its start limit; the
accounting guard correctly refused normal startup. No counter snapshot or
configuration switch had begun. RAM and volatile authority were retained for
diagnosis, without a reboot, password attempt or counter reset.

A separate fresh
[stock emergency-console baseline](../../experiments/m83/results/stock-emergency-console-baseline.json)
then proved a real no-echo root password prompt and authenticated shell before
any LocalPIN or counter fixture. The VM has only the kernel `tty0` console;
the attached emulated serial port is not a kernel console. Source review found
that the empty maintenance target could complete before display-manager/logind
stop jobs. The corrected target explicitly orders those stop jobs before the
freezer/kill barrier so normal virtual-terminal cleanup can finish. That is a
concrete ordering correction; the exact native sulogin exit cause was not
observed. Final-candidate recovery evidence is recorded separately.

Candidate `.10` then passed
[actual worker crash and same-boot accounting recovery](../../experiments/m83/results/actual-worker-crash-recovery.json):
the authenticated root emergency shell invoked the installed helper, original
volatile policy and failure history were preserved, the journal became aborted,
and login/network services returned. The graphical handoff stopped the console
before its observer captured the helper return code; the record reports that
value as unavailable and verifies the actual resulting state instead.

That result did **not** complete normal-flow acceptance. The subsequent owner
password login rendered Plasma but
[failed to start its user manager](../../experiments/m83/results/post-recovery-user-manager-failure.json)
with `ENOENT`, leaving no session bus and no delegated `init.scope` child.
A new root user manager worked. Both user-manager and runtime-directory units
ignore ordinary isolation. A
[diagnostic ordinary stop of `user.slice`](../../experiments/m83/results/diagnostic-user-lifecycle-drain.json)
followed by a real password login regenerated the manager, bus and delegated
subgroup while preserving the non-owner history. This was fixture remediation,
not a passing retry of `.10`. The final target explicitly conflicts with and
orders itself after `user.slice`, draining that lifecycle before freezing
survivors. The observations support this correction; they do not prove the
exact failing native spawn syscall.

The [idle-lock fixture failure](../../experiments/m83/results/fixture-idle-lock.json)
also remains failed: a driver expected the setup window after the VM had idle
locked. It stopped without requesting maintenance or isolation. The account was
unlocked with its real synthetic password, with no manual counter reset. The
corrected observation/input fixtures require an unlocked graphical session.

The [VT-specific observer refusal](../../experiments/m83/results/fixture-emergency-vt-refusal.json)
occurred after an authenticated emergency shell opened on VT2 while the fixture
expected VT1. It refused before invoking product recovery. The actual terminal
was verified and only the observer expectation corrected, without another
password attempt or a product-state edit.

Actual KDE password unlocking passed on the stock baseline. Installed normal-user
setup reached the saved-work maintenance prompt through real sudo. Cancelling
left native policy, the separate account's nonempty failure tally, desktop
integration and authority unchanged.

The first confirmed maintenance run on
`localpin-0.1.0-0.1.alpha1.vm83.3.fc44.x86_64.rpm` stopped at the cgroup preflight
in phase `quiescing`, before any counter snapshot/copy or configuration switch.
It selected emergency recovery, where the stock root account was locked. The
[retained failure record](../../experiments/m83/results/initial-maintenance-failure.json)
is explicitly failed. RAM and volatile accounting were preserved in a managed
save for diagnosis. The subsequent implementation adds bounded root-private
failure diagnostics and a verified same-boot abort for untouched requests so
that this early refusal restores normal password login. The later successful
installed cases are recorded separately above; historical M8.2 evidence does
not establish them.

The separate
[pre-barrier safe-abort observation](../../experiments/m83/results/pre-barrier-safe-abort.json)
passed on RPM `0.1.0-0.1.alpha1.vm83.4.fc44`. The deliberately retained strict
preflight refused the stock layout, then restored display manager, logind,
SSH, NetworkManager and user-session startup. The same-boot volatile policy and
the non-owner account's nonempty counter bytes/security metadata were unchanged;
no backup, persistent copy, enrollment authority or resume hint was created.
An actual password login through the display manager succeeded afterward.
This is successful refusal recovery, **not** a successful migration.

The actual guest inventory established that root-cgroup tasks were kernel
threads (`Kthread: 1`) and six stock top-level mount cgroups were empty. The
corrected preflight admits only those explicitly reviewed empty mount groups
and kernel-only root tasks, includes the mount groups in the kernel barrier,
and rechecks the topology after freezing PID1. A durable `barrier-started`
phase prevents an in-barrier failure from qualifying for untouched-state abort.

## Development review

A separate implementation agent reviewed the privileged service, recovery,
packaging and wizard boundary. Findings fixed before final acceptance include a
watchdog parent-PID race and PID reuse (now signaled through an inherited
pidfd), private backup mode validation, recursive backup
relabeling, symlink helper loading, restoration self-isolation, ownership of
temporary masks and bounded state. Recovery and barrier-order regression tests
were added. The final separate implementation pass checked watchdog descriptor
cleanup, the fixed privilege boundary, automatic resume, the boot guard, package
lifecycle and backup-label preservation; it found no remaining actionable issue.
These are AI development reviews, not M9's required independent specialist review.

A final concurrency pass found that a package transaction already past its
scriptlet checks could overlap the delayed maintenance handoff. The final
implementation acquires the verified native RPM POSIX transaction lock before
request creation and before any worker mask/isolation command. It rechecks
policy under the lock, retains exclusion through verification/restoration, and
refuses a busy package manager without disturbing the desktop. Real
cross-process lock tests cover both orderings and cleanup; a durable untouched
marker prevents early lock failures from invoking emergency isolation. The
independent final review of this correction found no remaining actionable issue.

## Remaining validation limits

The installed interruption case kills the worker at the confirmed frozen
quiescent boundary. Source fixtures cover additional phases and verified
post-switch forward recovery; this record does not claim an installed power-cut
test at every journal, fsync or configuration-switch boundary. The complete PIN
enrollment/activation and active lifecycle cases retain their exact `.5`/`.6`
build scope; the final `.11` changes have the targeted installed evidence above.

These results cover one stock Fedora KDE 44 VM layout with an emulated TPM and
synthetic credentials. They do not establish physical TPM/fingerprint support,
other filesystems or desktop distributions, M9 independent human/specialist
review, or reconciliation of a final signed release candidate.
