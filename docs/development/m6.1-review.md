# M6.1 development review

Date: 2026-10-17. Scope: production lifecycle/storage, password-free eligibility,
native policy-worker supervision, broker composition, diagnostics and the guarded
real-account evidence fixtures.

Separate agents reviewed lifecycle/storage, eligibility/native PAM and
broker/CLI integration. Findings were corrected and the affected paths received
fresh review. This is **AI-assisted development review**, not M9's independent
human/specialist authentication, confinement or hardware review. The author of
this report assembled the findings and check records; that assembly is not an
additional independent review of the implementation.

## Findings and corrections

- Existing-user storage could recreate a missing permanent UID-lock inode.
  That could split serialization from a guard retaining the original inode.
  Ordinary user access now requires the existing lock and refuses missing or
  unsafe state. Only privileged offline reprovisioning creates a new disabled
  baseline under the global exclusive lifecycle lease. Root quarantine handles
  corrupt old metadata without following or normalizing it, and keeps bounded,
  separately synchronized historical state.
- Initial missing-tally provisioning exposed the final name before ownership
  and mode were canonical. A crash could leave state that every later seal or
  recovery refused. Provisioning now prepares an unnamed `O_TMPFILE` inode,
  completes ownership/mode and file synchronization, publishes with no-overwrite
  `linkat(AT_EMPTY_PATH)`, then synchronizes the directory. Crashes before link
  leave no final path; crashes after link leave canonical state. Tests cover all
  six boundaries and prove an existing accounting record's bytes and metadata
  cannot be overwritten by a creation race.
- Native policy work needed explicit socket cancellation/disconnect monitoring.
  The retained peer monitor now observes pending cancellation and disconnect
  while the bounded policy child runs. Cancellation kills/retires the child and
  retains its process/UID slot until reaping. Integration review also checked
  the 100 ms policy-response reserve: it subtracts from the original deadline,
  and cannot extend the outer request or suppress the original PAM delay or
  accounting.
- A parallel peer-monitor regression assumed immediate EOF after dropping one
  socket descriptor. It failed the complete run while passing alone because a
  concurrent child could briefly inherit the endpoint. The regression now
  explicitly shuts down the socket before closing it. The subsequent complete
  localpind runs passed, including the final 53-test run. This corrected the
  fixture's assumption; it was not presented as an authorization bypass.

## Actual writer bypass and revised proof

The disposable Btrfs guest disproved the initial immutable-only design:
`pwrite` through a descriptor opened writable before sealing still succeeded.
The domain was revoked and the guest repaired. This failed experiment was
never accepted as account-continuity evidence.

The revised design sets immutable flags, then acquires Linux
`F_SETLEASE(F_RDLCK)` leases on every protected regular input. The kernel rejects
an existing writable descriptor or shared writable mapping, including a mapping
whose original descriptor has closed. The manager retains all read leases
through durable active-registry publication. After the registry temporary-file
fsync, immediately before rename, the final gate checks every `F_GETLEASE`
result, immutable flag and the complete unchanged input snapshot. Failed
acquisition or final checks leave the durable registry revoked.

Independent re-review examined lease lifetimes and the small, function-scoped
unsafe `fcntl` integer-argument boundary. Native temporary-file regressions
require the expected `EAGAIN` refusal with an old writer or mapping and successful
lease acquisition after it drains. Another regression proves a missing final
lease prevents active registry publication. The `LPACCT02` schema explicitly
rejects experimental format 01; root recovery generates fresh disabled
incarnations rather than adopting continuity from the earlier design.

## Real-authority scheduling fixture review

The `m61-fences` example delegates lifecycle/eligibility decisions to actual
`SystemAuthorities`, retains the actual returned lifecycle authority and lease,
and uses the production `ProtectedEngine`, storage and installed workers. Its
only added behavior is a single pause of at most 500 ms at an observed staging,
pointer-publication, durable-success or granted-delivery point. It rechecks the
actual lifecycle after a lifecycle pause and forwards the actual verifier's
outcome and original deadline. No synthetic incarnation, eligibility result,
password grant or PIN result is supplied.

The runner's fresh disabled generation-one, absent generation-two and absent
top-level pending-pointer preconditions address the concern that a staging or
publication pause could observe an old artifact. The success case compares the
actual durable throttle to its startup attempt counter. Concurrent root mutation
must return Busy without changing the incarnation; after release the actual
operation must complete, subsequent durable revocation must succeed and the old
PIN must be refused. The runner rejects a pause exceeding 500 ms. Guards require
the dedicated KVM clone's root-controlled DMI marker, Fedora KDE, SELinux
Enforcing and no TPM device. Secrets travel over private pipes and are absent
from result records. The ordinary production executables gain no fixture mode.

Source review found no authority substitution or deadline extension in this
fixture. Its exact four-point VM results and final artifact identities belong
to the [M6.1 evidence report](m6.1-account-authorities.md). A rapid-restart failure
in the clone component units was treated as fixture infrastructure; the runner
resets only those explicitly named test units before restarting them.

## Remaining boundaries

No further concrete authorization bypass was identified in the reviewed final
paths. This statement is limited to this development review and its evidence.
Ordinary unmanaged accounts remain unavailable, appliance mutation requires
global revocation and fresh enrollment, and lost volatile faillock state after
reboot requires explicit privileged recovery. These costs are part of the
supported domain, not hidden compatibility assumptions.

M7 retains actual stock KDE PIN/fallback integration. M8 retains installed
password-worker/systemd confinement, full SELinux/RPM lifecycle, activation and
console recovery. M9 retains human/specialist review and physical TPM/hardware
validation. Administrative-domain component tests with SELinux Enforcing do not
complete those gates or authorize everyday-host activation.
