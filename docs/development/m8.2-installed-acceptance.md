## Disposable environment and observation

The run uses an independent Fedora KDE 44 x86_64 KVM clone with SELinux
enforcing, Btrfs, a private managed TPM 2.0 emulator and synthetic accounts.
The original VM stays off. Active/inactive libvirt topology checks prohibit
backing/shared disks, host filesystem shares and physical device/TPM passthrough.
Pinned SSH/guest-agent access supports guarded observations. Terminal and
lock-screen input uses libvirt keyboard events. VT activation used keyboard
hotkeys and, when their timing guard did not establish the requested VT, a
separate topology-guarded SSH `chvt` operation. Actual VT3 administrator origin
was checked independently through the active virtual terminal, native session
and sudo ancestry; this is not a claim that every VT switch used the keyboard.

The wizard runs the installed executable in an actual KDE Konsole through the
existing user's systemd manager. Distribution `script` supplies its foreground
PTY and records output only to a root-only-readable guest log. Real sudo and
account-password prompts remain separate; credentials never enter arguments,
environment variables, exported results or source files. Private synthetic
input transport is confined to the acceptance harness. An operator's test
confirmation remains an attestation; the actual UI observations are separate.

## Fixture failures and explicit disposition

The failed observations are retained; none is relabeled as a passing attempt.

1. Accounting runner `12eff7a6…` refused before backup/copy/configuration change
   because a genuinely native-created mode-0660 tally had the owner's primary
   GID. The reviewed offline instructions and fixture now require explicit
   destination-only GID canonicalization. Production GID-0 validators stay
   unchanged. Exact original metadata and counter history are backed up.
2. Runner `997dc896…` refused before copying because a real KDE locker worker
   survived graphical logout while the same UID remained logged in on VT3.
   Runner `752f10ff…` explicitly stopped the user manager's graphical-session
   and Plasma workspace targets, retained the quiet-process/session checks and
   completed migration. Narrow, separately reviewed retry options preserved
   both previous intents, failures and restoration evidence.
3. Console runner `42b0b4e7…` completed its actual dry-run and recovery, then its
   post-verifier required a gate file that native revocation intentionally
   removes. Missing gate means disabled in production. Observer `e48d5464…`
   accepts absent/canonical-disabled gate and has a narrowly bound
   observation-only completion mode: it preserves the original failure and
   command records, checks original source/helper/UUID/boot and current
   postconditions, and never repeats recovery or authentication. This observer
   passed; its [standalone sanitized result](../../experiments/m82/results/actual-console-recovery.json)
   retains the distinct command and observer source hashes.
4. The first post-recovery password test selected a phase requiring an unlocked
   desktop, while KDE was already locked. Its guard refused before input. The
   explicit existing-lock password phase then passed. An optional PIN-rotation
   attempt stopped before writing because its read-only broker check was
   unavailable; that attempt did not rotate the PIN. The later successful
   fixture-only rotation and fresh enrollment are recorded separately above.
5. Subsequent sudo refused under native lockout after three valid failure
   records. The test controller repeated password prompts before being stopped;
   the wizard was canceled with exit 130 and retained the tally. The original
   stock fingerprint/password graph retains the accounting behavior documented
   in [ADR 0018](../adr/0018-kde-native-update-compatibility.md): graphical
   password success does not imply an account-phase tally reset. The run waited
   out the native 600-second unlock interval without counter edits or factor
   disablement. At a latest-record age of 622 seconds, one ordinary sudo
   authentication succeeded and its native account phase cleared the tally
   legitimately. The subsequent fresh wizard preparation/enrollment and real
   desktop tests passed; this does not relabel the earlier lockout/cancellation.
6. After observing natural expiry, the controller prematurely requested the old
   wizard's completion while it still waited at an ordinary sudo password
   prompt. The fixture correctly refused incomplete evidence. The next wizard
   then replaced the trial before the old surface was authenticated once and
   returned its stale-trial refusal. These observations establish natural gate
   expiry and refusal after trial replacement during reauthentication; they do
   not isolate a deadline-only activation-refusal branch. No old-case test
   attestation was written and no activation was reported.
7. The first active no-op's function completed, but its exact-state assertion
   correctly refused a native-tally difference: 128 bytes became zero through
   ordinary sudo's successful native account phase. A separate review proved
   all other protected bytes, metadata and services equal. The original failed
   assertion is retained; a repeated active no-op from an empty tally passed
   exact comparison. No counter-reset command was used.
8. The first correct-candidate post-upgrade graphical PIN attempt remained
   locked for the 15-second observation interval. Its output file is empty
   after the failed controller run and supplies no passing UI result. Read-only
   TPM properties showed dictionary-attack counter 1, maximum 3 and recovery
   interval/lockout recovery 1,000 seconds. The production reserve rule requires
   remaining attempts to exceed 2; the measured remainder was 2. This supports
   an expected reserve-refusal assessment from source and properties, not a
   captured `Error::Budget` trace. Public broker availability and zero cooldown
   do not probe TPM budget. No reset or TPM configuration change occurred;
   natural recovery and a later actual PIN observation remain pending.

The [fixture instructions](../../experiments/m82/README.md) explain these
boundaries. Thirteen isolated fixture tests, Python compilation and whitespace
checks passed at this report checkpoint. Independent agent review is useful
development feedback; it is not the M9 independent human/specialist review.
